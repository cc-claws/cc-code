## 1. 方案 B：user-role 片段

**核心**：把 `!` 命令表示为 **role=user 的上下文片段**，标签形态参照参考实现。

```xml
<!-- 消息 1：命令 -->
<bash-input>git push -u origin fix/x</bash-input>

<!-- 消息 2：结果（peri 双流分离，故 stderr 独立；见 §4.2 IM-1） -->
<bash-stdout>To https://github.com/...</bash-stdout><bash-stderr>…</bash-stderr>
```

**为什么选 B**（§10-D1 决策）：

| | A（assistant tool_use，v3/v4） | **B（user 片段，本版）** |
|---|---|---|
| 参考实现 | ✗ 相反 | ✅ 同为 user-role |
| 模型归因 | 「**我**执行了」→ 可能误判、重复执行 | 「**用户**执行了」→ 归因正确 |
| I2 语义 | 需纠结 `is_error` 该不该置位 | ✅ 无 `is_error` 概念，天然规避 |
| I5 resume | 渲染为 Bash 工具卡片（幽灵） | ✅ 走 `Human` 路径（仍需跳过，见 §4.6） |

**参考实现的关键细节（已核实 `/d/code/cc-best-src`）**：

| 项 | 内容 |
|---|---|
| 命令消息 | `createUserMessage({ content: "<bash-input>…</bash-input>" })`（`processBashCommand.tsx:42-47`） |
| 结果消息 | `createUserMessage({ content: "<bash-stdout>…</bash-stdout><bash-stderr>…</bash-stderr>" })`（`:137-139`） |
| 执行 | 复用 `BashTool.call`（同一工具、同一格式化管线，`:103-126`） |
| **⚠️ caveat 前置消息** | **`createSyntheticUserCaveatMessage()`（`:134`），见下方 IM-3** |
| 不触发推理 | `shouldQuery: false`（`:141`） |
| 回放渲染 | `UserTextMessage.tsx:64-65` 识别 `<bash-stdout`/`<bash-stderr` → `UserBashOutputMessage` 专用组件 |
| caveat 的 UI 隐藏 | `UserTextMessage.tsx:58-61` 返回 `null` |

### 1.1 ⚠️ IM-3：参考实现的 caveat 消息（v5 遗漏，v6 补入）

参考实现返回 **4 条**消息（`processBashCommand.tsx:133-140`），其中**第一条**是：

```xml
<local-command-caveat>Caveat: The messages below were generated by the user while
running local commands. DO NOT respond to these messages or otherwise consider them
in your response unless the user explicitly asks you to.</local-command-caveat>
```

（常量 `LOCAL_COMMAND_CAVEAT_TAG = 'local-command-caveat'`，`constants/xml.ts:13`；构造见 `messages.ts:569-575`）

**已核实其性质**：

- `isMeta: true` —— 但**只被 UI 隐藏**（`UserTextMessage.tsx:58-61` 返回 `null`）

**为什么必须有**：没有它，模型会把「用户在执行本地命令」误读为「用户下达了指令」——
这正是 §1 表格所担心的归因问题，参考实现靠这条 caveat 兜底。**v5 声称「与参考实现完全一致」却漏掉了它。**

**处置：定案 C1（注入等价 caveat）**

采用 C1：在两条片段前再注入一条 `Human` caveat 消息，文案对齐参考实现：

```xml
<local-command-caveat>Caveat: The messages below were generated by the user while
running local commands. DO NOT respond to these messages or otherwise consider them
in your response unless the user explicitly asks you to.</local-command-caveat>
```

**必须配套的两点**（否则引入新缺陷）：

1. **TUI 必须隐藏**（K12）：peri 的 `BaseMessage` 无 `isMeta` 字段（已核实），
   故 caveat 会作为普通 `Human` 进入历史 → 必须在 `messages_to_view_models`
   与 `bash-*` 片段**同处跳过**（§4.6），否则用户会看到这条英文 caveat。
2. **Caveat 的位置**：需在**两条片段之前**（时序上先于命令），且**每次注入一组**（不跨命令复用）。

> **备选 C2/C3 已否决**：C2 偏离参考实现且丢失「不要响应」的显式语义；C3 风险最高。

> **新增约束 K12**（**已核实**）：`BaseMessage`（`peri-agent/src/messages/message.rs:59-90`）**无 `isMeta` 字段**，
> 且全仓无等价的 meta 语义表达（`grep is_meta|isMeta` 在 `peri-agent`/`peri-tui` 非测试代码中无命中）。

## 4. 详细设计

### 4.1 服务端：`session/append_history`

**落点**：`run_acp_server` 主循环内联拦截（`acp_server/mod.rs:100` 一带，与 `session/prompt` 同层），复用 `prompt_locks`（K9）。

> **I7 修正**：v3 此处写 `handle_request` 的 `match` 臂，与 §4.1.1 结论矛盾；本版统一为主循环拦截。

**载荷**：`BaseMessage` 序列化数组。serde 形态（已核实 `message.rs:59-90`）：`#[serde(tag = "role")]`，
变体重命名为 `"user"`/`"assistant"`/`"system"`/`"tool"`。本方案只用 `Human`（`role="user"`）：

```jsonc
{
  "sessionId": "...",
  "messages": [
    { "role": "user", "id": "<uuid>", "content": "<bash-input>git push -u origin fix/x</bash-input>" },
    { "role": "user", "id": "<uuid>", "content": "<bash-stdout>…</bash-stdout><bash-stderr>…</bash-stderr>" }
  ]
}
```

**处理逻辑**：

```rust
} else if method == "session/append_history" {
    let sid = extract_session_id(&params, "").to_string();
    let lock = {
        let mut locks = prompt_locks.lock().await;
        locks.entry(sid.clone())
            .or_insert_with(|| Arc::new(tokio::sync::Mutex::new(())))
            .clone()
    };
    let sessions = Arc::clone(&sessions);
    let transport = Arc::clone(&transport);
    let thread_store = cfg.thread_store.clone();
    tokio::spawn(async move {
        let _guard = lock.lock().await;                    // 与 session/prompt 串行（§4.1.1）
        let messages: Vec<BaseMessage> = params.get("messages")
            .map(|v| serde_json::from_value(v.clone()).unwrap_or_default())
            .unwrap_or_default();
        if messages.is_empty() {
            let _ = transport.send_response(id, Err(AcpError::new(-32602, "missing messages"))).await;
            return;
        }
        let mut sessions = sessions.lock().await;          // Arc<tokio::sync::Mutex<HashMap<..>>>
        if let Some(state) = sessions.get_mut(&sid) {
            state.history.extend(messages.clone());
            let tid = ThreadId::from(state.thread_id.clone());
            if let Err(e) = thread_store.append_messages(&tid, &messages).await {
                tracing::warn!(error = %e, "append_history persist failed");
            }
        }
        drop(sessions);
        let _ = transport.send_response(id, Ok(json!({ "accepted": true }))).await;
    });
```

#### 4.1.1 并发论证（v6 重写，B2 / IM-2 双重修正）

**两次错误论证的证伪记录**（保留以示教训）：

| 版本 | 错误断言 | 证伪依据 |
|------|---------|---------|

| v5 | 「`!` 结束后下一帧 `poll_background_shell_events`/`poll_agent_shells` → `submit_message`」 | 二者**只遍历 `background_shells`（Ctrl+B 后台化）与 `agent_shells`（BashTool）**；前台 `!cmd` 完成后**既不入两者**，`poll_foreground_shell`（`:203-269`）仅调 `handle_shell_command_completed`；且 `AgentEvent::ShellCommandCompleted` **无任何发射点**（全仓仅 match 臂，`events.rs:14`、`agent_ops/mod.rs:19`、`message_pipeline/mod.rs:550`） |

**修正后的论证（结论不变，证据改为结构性事实）**：

| # | 事实（已核实） | 证据 |
|---|--------------|------|
| C1 | prompt 结束**整体赋值**回写 history | `prompt.rs:187` |
| C2 | `execute_prompt` 启动时克隆 history，运行中不再读取 | `prompt.rs:90`；`executor.rs:610` |
| C3'' | **并发来源是「用户紧接着提交下一条 prompt」**，与 fire-and-forget 的 `append_history` 竞争 | 正常交互路径：`main.rs:939-940` `Action::Submit` → `agent_submit.rs:271-306` |

**可达路径（简化为最朴素的形式）**：

```
!cmd 完成 → fire-and-forget 发送 append_history
          → 用户立即输入下一条消息并回车
          → session/prompt 启动：克隆 history（C2）→ 执行 → 整体回写（C1）
          → 【危险窗口】append_history 抵达并写入 state.history
          → 被 :187 覆盖 → 注入丢失
```

**注意**：即便 `mpsc` 是 FIFO，`append_history` 与 `session/prompt` 也被**分别 `tokio::spawn`**
（`append_history` 见 §4.1 伪代码；`session/prompt` 见 `acp_server/mod.rs:146`），
故二者的 `state.history` 读/写仍需锁保护。

**结论**：必须串行化 → 复用 `prompt_locks`（§4.1 伪代码 `lock.lock().await`）。

> **v5 勘误（IM-2）**：v5 以「下一帧轮询自动触发」为证据 —— 该路径**不存在**。
> 结论（需锁）正确，但 v5 的证据是**第二次**同类错误（与 v3-B2 同源：把不存在的自动触发当作并发来源）。

**构造函数**：

```rust
// peri-tui/src/app/shell_command.rs
/// 将前台 ! 命令构造为 role=user 的两条上下文片段（标签形态参照 claude-code-best）。
fn shell_context_messages(record: &ShellCommandRecord) -> Vec<BaseMessage> {
    // C1：先注入 caveat（对齐参考实现，防止模型把命令回放误当用户请求）
    let caveat = BaseMessage::human(SHELL_CAVEAT);   // 常量见 §1.1

    let input = BaseMessage::human(format!(
        "<bash-input>{}</bash-input>",
        xml_escape(record.command.trim())
    ));

    // peri 的 stdout/stderr 分开捕获（shell_exec.rs:24-28），故拆入两个标签。
    // 注意：这与参考实现的 merged-fd 语义不同（见下方 IM-1 更正），属有意偏离。
    let stdout_body = format_command_output(&record.stdout, "", record.exit_code);
    let output = BaseMessage::human(format!(
        "<bash-stdout>{}</bash-stdout><bash-stderr>{}</bash-stderr>",
        xml_escape(&truncate_shell_output(&stdout_body)),
        xml_escape(&truncate_shell_output(&record.stderr)),
    ));

    vec![caveat, input, output]      // 顺序：caveat → 命令 → 结果
}
```

**为什么传 `stderr: ""`** —— **v6 更正（IM-1）：v5 对此的解读是错误的**

v5 曾称「参考实现**刻意**分离 stderr 以保持标签独立」。**实际相反**（已核实 `/d/code/cc-best-src`）：

- `BashTool.tsx:825` 注释原文：`// stderr is interleaved in stdout (merged fd) — result.stdout has both`
- `data.stderr` 实为 `stderrForShellReset`（`BashTool.tsx:771` 初始化为 `''`），**仅在 cwd 被重置等异常场景赋值**（`:846`/`:857`）
- 故参考实现的 `<bash-stdout>` **包含命令的 stdout 与 stderr 合并体**，`<bash-stderr>` 在正常路径下**几乎恒为空**
- `stderr: ''` 的用途是**不把 shell-reset 提示折进格式化结果**（`processBashCommand.tsx:122-125` 注释），而非分离命令 stderr

> 本方案传 `stderr: ""` 的**自身理由**：`format_command_output` 会在 stderr 非空时插入 `[stderr]` 段落
> （`terminal.rs:81-87`）；既然 stderr 已由独立标签承载，此处传空可**避免重复**。

**peri 的现实与参考实现不同**：`CommandOutput` 的 stdout/stderr **分开捕获**（`shell_exec.rs:24-28`，独立 `Stdio::piped()`）。

**要点**（已核实）：

| 项 | 处理 | 依据 |
|---|---|---|
| `<bash-stdout>` | `format_command_output(stdout, "", exit_code)` —— **含退出码** | `terminal.rs:76-95` |

### 4.3 TUI 侧：发送

`handle_shell_command_completed` 末尾追加（`shell_command.rs:925-978`）：

```rust
if let Some(ref acp_client) = self.acp_client {
```

- **M2 修正**：v3 依赖 `current_session_id`，切换会话时会串到错误 session；本版显式传目标 id。

### 4.4 ACP 客户端方法

```rust
// peri-tui/src/acp_client/client.rs（需 +use peri_agent::messages::BaseMessage;）
pub async fn append_history(
    &self,
    session_id: String,
    messages: Vec<BaseMessage>,
) -> Result<(), String> {
    let params = json!({ "sessionId": session_id, "messages": messages });
    self.transport
        .send_request("session/append_history", params)
        .await
        .map(|_| ())
        .map_err(|e| e.to_string())
}
```

### 4.5 时序与一致性

```
!git push（agent 空闲，K6）
  → 执行完成 → handle_shell_command_completed
  → 构造 [<bash-input>, <bash-stdout>] → append_history(thread_id, ...)（fire-and-forget）
  → 服务端：取 prompt_lock → state.history.extend + thread_store.append_messages
  → 用户下次提问 → session/prompt 读到含片段的 history → 模型可见
```

持锁保证两方向安全：注入先于 prompt → 本轮可见；注入后于 prompt → 落在 `:187` 回写之后，不被覆盖。

### 4.6 resume / 实时显示（I5 解决 —— 已用**实证**取代推断）

**实证结论（2026-09-30，探针测试实测）**：

对两条片段消息调用 `MessagePipeline::messages_to_view_models`，输出为：

```
[0] UserBubble { content: "<bash-input>deploy --prod</bash-input>", rendered: "deploy --prod" }
[1] UserBubble { content: "<bash-stdout>done</bash-stdout>…",      rendered: "done" }
```

即：

| 观察 | 结论 |
|------|------|
| **markdown 解析器把 `<bash-*>` 当作 HTML 标签吃掉** | ✅ **不会泄露原始 XML**（最坏情况不存在） |
| 渲染结果为 `UserBubble`，`system_reminder: false` | ⚠️ 会显示为 **2 个用户气泡** |
| `shell_notification_display_text("<bash-input>…")` 返回 **`None`**（实测） | ❌ **K10 推论不成立** —— 该函数不识别 `bash-*` 标签 |

> **v5 勘误**：v5 §4.6 声称「复用 `shell_notification_display_text` 钩子即可渲染为 `SystemNote`」——
> 经实测**不成立**。`BaseMessage::Human` 分支确实首查该函数（`message_view/mod.rs:607-614`，此点无误），
> 但该函数对 `bash-*` 返回 `None`，故片段落入常规 `UserBubble` 路径。

**因此 BL-1（重复显示）确认成立且形态明确**：

```
open_thread (thread_ops.rs:175-213)
  ├─ messages_to_view_models(base_msgs)      → 片段 → UserBubble × 2      ← 数据源：ThreadStore
  └─ merge_shell_records_into_view(...)      → 真实 ShellCommand VM        ← 数据源：shell-commands.jsonl
```

两数据源独立、**无去重** → 同一条 `!cmd` 在 resume 后**必然出现两处**（气泡 + ShellCommand 卡片）。
**实时路径同理会因此抖动**：ACP `StateSnapshot` 会带着片段回流（`message_pipeline/mod.rs:534-540`
`set_completed(msgs)` → `build_tail_vms` → `messages_to_view_models`，`reconcile.rs:199`）。

**处置（唯一收口点方案，推荐）**

`messages_to_view_models`（`transform.rs:66`）是**实时与恢复的共同收口**，且**已有跳过范式**：

```rust
// transform.rs:70-74 现存范式
if matches!(msg, BaseMessage::System { .. }) { continue; }        // System 是内部状态，不渲染
// transform.rs:86-95 现存范式
if let MessageViewModel::AssistantBubble { blocks, .. } = &vm {
    if !has_visible { continue; }                                  // 无可见文本的 Ai 不渲染
}
```

照此新增一条跳过规则（**需精确限定，避免误伤正常用户消息**）：

```rust
// 内部上下文片段（前台 ! 回流 + caveat）不渲染 —— 由 ShellCommand VM 负责展示
if let BaseMessage::Human { content, .. } = msg {
    let t = content.text_content();
    if t.starts_with("<bash-input>")
        || t.starts_with("<bash-stdout")
        || t.starts_with("<local-command-caveat>")     // C1 的 caveat，须一并跳过（K12）
    {
        continue;
    }
}
```

**边界论证**（均为实测/已核实）：

- ✅ 正常用户消息以这三个前缀**开头**的概率可忽略；且参考实现同样依赖前缀匹配（`UserTextMessage.tsx:64` 用 `startsWith`）
- ✅ 流式侧不受影响：流式内容走 `push_chunk` 路径，非从 history 重建（`reconcile.rs:199` 仅对 `completed[start..]` 转换）
- ✅ 不影响 compact / 模型上下文 —— 仅改**展示层**（caveat 仍照常送达模型，这是 C1 的目的）
- ⚠️ 需为 `Human` 分支补单测（含「正常用户消息不被误跳」的反例）

**备选（不推荐）**：让 `shell_notification_display_text` 识别 `bash-*` 并返回摘要 —— 仍需处理与 ShellCommand VM 的重复，等于在错误层打补丁。

### 6.1 IM-4.2 边界：后台化 `!`（Ctrl+B）不走本方案

`background_foreground`（`shell_command.rs:423-496`）把前台 `!` 转入 `background_shells`，
其完成走 `poll_background_shell_events`（`:277`）→ `shell_completion_notification` + `submit_message`
（`:316-358`），**不经过 `handle_shell_command_completed`**，故：

| 形态 | 行为 |
|------|------|
| 前台 `!` | 注入片段（本方案），**不触发新轮次** ✅ 符合目标 |
| Ctrl+B 后台化 `!` | 走既有后台通知 + **额外起一轮 agent**（既有行为，本方案不改） |

**结论**：两者行为**不对称**，但均为各自既有设计的延续。本方案**不改后台链路**，
仅在文档中显式记录该不对称，避免实现者误解为缺陷。

### 6.2 IM-4.3 边界：`acp_stdio` 未注册新方法

`run_acp_stdio`（`peri-tui/src/acp_stdio.rs`）有**独立的** `session/prompt` 处理路径，
未走 `run_acp_server` 主循环。若 peri 以 stdio 形态作 ACP server（IDE 集成场景），
`session/append_history` 会命中 `requests.rs` 的兜底分支（method not found）。

**结论**：本方法**仅 TUI 内嵌 server 需要**（TUI 是唯一发起 `!` 的宿主）。
stdio 形态下 TUI 侧 `append_history` 会失败 → 静默降级（§4.3 已有处理）。**需在文档显式声明。**
