# 含 `⚠️` 的表格行在终端上多占 1 列，右侧边框冲出表格并留下错位残影

**状态**：Fixed
**优先级**：中（仅影响显示，不影响数据；但表格是 agent 输出的主要信息载体，错位会让整行内容不可信）
**创建日期**：2026-11-03

---

## 一、问题描述

agent 输出的 markdown 表格里，只要某一行的单元格含 `⚠️`（`U+26A0 U+FE0F`，带 VS16 变体选择符），该行在 TUI 上就会**比其他行多占 1 个字符格**：

- 该行内部的竖线分隔符、以及表格最右竖边框，整体右移 1 格；
- 右边框落到表格边界之外，右侧空白区出现一根悬空的孤立竖线（截图红框处）；
- 表格右下角还残留若干不与任何边框相连的竖线片段。

同一张表其余 8 行（不含 `⚠️`）完全对齐。

**交互现象**：在出错那一行上**双击（触发整块重绘）后显示恢复正常**；但滚动离开再滚回来，错位又重新出现。

## 二、症状详情

原表格（会话 `01a1a013-34d0-7391-82e5-8ec210bd5bd6`，消息 `01a1a015-e5e1-75c1-9f44-2c53e60bb8c4`）中该行为：

```markdown
| ⚠️ `cc-switch` | `fix/gemini-thought-signature` | `https://oauth2:gho_...@github.com/cc-claws/cc-switch.git` |
```

`⚠️` 实为两个码位：

| 码位 | 字符 |
|------|------|
| `U+26A0` | WARNING SIGN |
| `U+FE0F` | VARIATION SELECTOR-16 |

### 屏幕实测（按 9px/字符格逐列量取）

| 行 | 左边框 | 第 2 条竖线 | 表格最右竖线 |
|----|--------|-------------|--------------|
| `cc-best-src`（对照） | col 0 | col **16** | col **129** |
| `codebuddy-hud`（对照） | col 0 | col **16** | col **129** |
| **`⚠️ cc-switch`** | col 0 | col **17** | col **130** |

- 多出的 1 格出现在 `cc-switch` 文字之后、闭合边框之前（内边距区），文字本身未偏移；
- 表格顶/底横边框仍是 130 列宽，与数据行 131 列不匹配，视觉上即「右边框冲出表格」。

### 宽度口径对照（真实控制台式实测量取）

| 写法 | `unicode-width` 判定 | 真实控制台推进 | 是否一致 |
|------|---------------------|---------------|----------|
| `⚠️`（`U+26A0 U+FE0F`） | 2 列 | 2 列 | 一致 |
| `⚠`（仅 `U+26A0`） | 1 列 | 1 列 | 一致 |
| `表`（CJK） | 2 列 | 2 列 | 一致 |

> 注：上表是本机 Windows 控制台（VT 路径）的实测值。**终端本身对 `⚠️` 的宽度判定与 `unicode-width` 一致**，问题不在字形宽度，而在输出层如何下发这一格的相邻 cell（成因见第五节第 4 条）。

## 三、复现条件

- **复现频率**：必现（只要表格某行含 `⚠️`，该行即外扩 1 格），与终端/字体无关，取决于输出层是否补画尾格（见第五节第 4 条）。
- **触发步骤**：
  1. 让 agent 输出一张 markdown 表格，其中一行单元格以 `⚠️` 开头；
  2. 观察该行右侧边框位置，与其他行对比。
- **加重现象**：
  1. 在出错行上双击 → 显示恢复正常；
  2. 滚动离开再滚回 → 错位复现，且表格右侧残留半截竖线。
- **环境**：Windows + peri TUI；截图来源为用户的终端会话（`thread 01a1a013…`，标题「查看下git分支详细」）。

## 四、涉及文件

- `cc-widgets/src/markdown/render_state.rs` —— 表格列宽分配、单元格折行与边框拼装（`wrap_cells` / `render_with_wrap` / `push_aligned`）。
- `cc-tui/src/terminal_backend/compatible.rs` —— 输出层按终端实测宽度做字形降级（`output_cell` / `ascii_fallback` / `fallback_symbol`）；当前降级表里有 `"⚠️" | "⚠" => '!'`，但只在「探针量出的宽度与期望不符」时触发。
- `cc-tui/src/terminal_backend/cursor_probe.rs` —— 终端列宽探针，只测「本应 1 列」的字形。

## 五、已验证的事实

1. **表格布局算法本身自洽**：把上述真实 markdown 直接喂给 `cc-widgets` 的 `parse_markdown`，21 行全部恰好 130 列宽，`┌/┬/┐` 与 `│` 位置逐字符对齐；穷举 `max_width` 40→200 无溢出、无行宽不一致。
2. **Buffer 分配正确**：渲染进 `ratatui::Buffer` 后，`⚠️` 占 2 个 cell，该行最后一个 `│` 落在预期 cell。
3. **本机控制台字形宽度正确**：把 `⚠️` 原样写入真实 Windows 控制台屏幕缓冲区再读回，推进 2 列，与 `unicode-width` 一致。
4. **真实成因在输出层，不在表格算法，也不在终端字形宽度**：`ratatui::Buffer::diff` 对含 VS16 的宽字形会**额外补画尾格**（防止部分终端不清尾格留残影）；而 crossterm 后端判断「能否连续打印」只看 **cell 索引**（`x == last.x + 1`），不认宽字形已按 2 列推进光标。于是尾格被当作相邻格直接续写，实际落到右边一格，**该行尾格之后的所有内容整体右移 1 列** —— 表格右边框因此冲出边界，右侧残留半截竖线。
   - 用复刻 crossterm 语义的模拟器可稳定复现：结尾竖线落在 col 17（应为 col 16）。
   - 这也解释「双击能修好、滚动又坏」：整块重绘时尾格与上一帧相同、diff 不补画；滚动触发增量 diff 后尾格被补画，错位随即出现。
