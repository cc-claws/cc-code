# [BUG] Windows 传统控制台下 Markdown 表格列宽错位、单元格硬断裂与物理屏幕溢出

**状态**：Fixed (已归档)
**优先级**：高  
**创建日期**：2026-09-20  
**模块**：TUI / Markdown 渲染 / Windows 终端兼容  
**GitHub Issue**：#163 (https://github.com/cc-claws/cc-code/issues/163)  

## 问题描述

在 Windows 传统控制台（CMD / conhost.exe，默认新宋体 8×16，CP936 代码页）下，TUI 渲染包含多列或长文本的 Markdown 表格时，发生严重的**边框垂直撕裂、列宽计算错位、单字/扩展名孤立断行、以及整行物理超出终端宽度被系统强制折行**的严重排版故障。

现场实测截图显示，表格各行右侧边界完全不对齐，上一行的行尾字符被物理折行打断并堆叠在下一行行首，导致整张表格完全不可读。

## 症状详情与现场证据

基于用户现场捕获的 5 列 Markdown 表格（Issue 清单）：

1. **整行超宽触发操作系统层强制物理折行（Hard Wrap）**：
   - 表格计算出的单行宽度超出了实际终端视口可用宽度；
   - 第一行末尾内容 `...Action Required 审批阻塞提醒、OSC` 直接撞到终端物理右边缘；系统控制台将溢出字符无条件折到下一物理行开头，将原有表格下半部分结构整体打乱。
2. **列宽计算分裂，垂直竖线完全对不齐**：
   - 表头与各行数据列的竖线 `|` 无法对齐，右侧竖线参差不齐；
   - 包含中文字符的列（如“拟定 GitHub Issue 标题”、“核心要点”）由于中文和中文标点在 CMD 点阵字体下的实际光标推进（东亚歧义宽度）与 `unicode-width` 逻辑列宽不一致，导致光标逐字向右漂移，后续单元格严重右偏。
3. **极端断词与孤立字现象**：
   - 长路径缺少保护断词：`spec/issues/...-issue.` 被硬切，文件扩展名 `md` 孤立掉在下一行（`| md |`）；
   - 中文字符在列宽极限处被暴力打断，单字单独成行（如“跨平台视觉自适应”的“应”字单独被甩在第 3 行：`| 应 |`）。
4. **制表符退化与字符破损**：
   - 原生 Unicode 精细制表符（`┌ ┬ ┐ │ ─ ├ ┼ ┤ └ ┴ ┘`）降级为 ASCII `-` 和 `|`；
   - 依赖字体的 Emoji（如秒表 `⏱`）在 CMD 下退化为乱码问号 `? Emoji`。

## 复现条件

- **终端环境**：Windows CMD (conhost.exe)、新宋体、代码页 CP936 或 CP65001。
- **触发步骤**：
  1. 启动 `peri` 或 `cargo run -p peri-tui`；
  2. 让 Agent 输出任意包含 3 列以上、包含中文字符或较长路径/URL 的 Markdown 表格；
  3. 观察消息流中的表格渲染呈现。
- **复现频率**：在窗口宽度 ≤ 120 列且表格列数 ≥ 3 时 100% 复现。

## 涉及文件

- `peri-widgets/src/markdown/render_state.rs` —— 表格宽度分配 `wrap_cells`、`distribute_col_widths` 与断行 `wrap_cell_text`
- `peri-tui/src/ui/markdown/mod.rs` —— TUI 视口最大宽度传递与 TableHoldbackScanner
- `peri-tui/src/terminal_backend/compatible.rs` —— Windows 输出层歧义宽度符号探针与适配

## 期望改进方案

1. **表格总宽度硬约束保护（Clamp to Viewport）**：
   - `render_with_wrap` 必须严格以当前可用终端可视宽度为硬上限，绝对禁止输出单行总宽度 > 终端宽度的行，彻底消除系统级强制折行。
2. **长单词/长路径智能截断与省略**：
   - 在单元格换行时，若遇到超长无空格路径（如 > 40 字符），采用路径中间省略截断（`path/.../file.md`），而不是任由其撑大列宽或截断出单字行。
3. **CJK 歧义列宽与字符保护**：
   - 为中文列设置合理的最小宽度（如 ≥ 8~10 显示列），防止剩余宽度只剩 1 时导致汉字（宽 2）被强行硬断；
   - 配合 `WidthSafeBackend`，保证终端物理光标推进与逻辑行宽度 100% 对齐。
